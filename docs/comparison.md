# GPUI 版與舊版（Tauri 2 + xterm.js）比較

舊版指 [`tauri` 分支](https://github.com/twtrubiks/ptt-desktop/tree/tauri)（v0.1.7）。
舊版有的功能 GPUI 版都已移植。

## 技術棧與架構

| 面向 | 舊版（Tauri 2 + xterm.js） | GPUI 版 |
|---|---|---|
| 執行環境 | 系統 WebView 載入 TypeScript 前端 | 純 Rust 單一執行檔，GPU 自繪，無 WebView、無 npm |
| 畫面模型 | xterm.js 原子寬字 cell，另維護 shadow 網格補修 | `grid.rs` 的 80×24 byte 網格就是唯一模型 |
| 雙色字／半字覆寫 | SGR 重排、PUA 拆字、疊繪 canvas、孤兒補寫 | 網格原生語意，繪製時用 content mask 各畫半邊 |
| 彩繪方塊 | 依賴捆綁字型的字形 | 幾何自繪，拼接無縫，字型用系統 Noto Sans Mono CJK TC |
| 閃爍、底線、游標 | 各自一層 overlay | `view.rs` 繪製時一次處理 |
| 字級 | 設定檔 `fontSize` | 由視窗大小反推 |
| 滑鼠滾輪 | xterm.js 內建，每個滾輪事件送一次 ↑／↓ | 一格送一次，自動登入進行中不送 |
| 圖片預覽 | WebView 的 `<img>` | 自寫 HTTPS client 抓圖並自行解碼 |
| 手動重連 | 等舊連線斷開再連，沒有間隔限制 | 另加 30 秒登入冷卻與線上二次確認 |
| 自動登入收尾 | 任何一步 10 秒逾時都報「中止」 | 密碼通過後逾時改為安靜交還；使用者一按鍵就交還 |
| 關視窗 | 連線隨程式結束切斷 | 先做完 WebSocket 關閉握手再結束 |
| 平台 | Linux／macOS／Windows | 只有 Linux |
| 程式碼量 | 約 2,500 行 TS，測試另 2,150 行 | 約 5,700 行 Rust（含寫在各檔內的單元測試） |

舊版八成的複雜度來自「xterm 一個寬字一個 cell」對上「PTT 一個 byte 一格」，為此長出
SGR 重排、PUA 拆字、疊繪、shadow 網格整條補償鏈。GPUI 版自己畫畫面，這條鏈不存在。

## 實測數字

環境：Debian 13、KDE Wayland、i7-1370P／32 GB，兩版皆為 release 建置。

### 啟動、記憶體、體積

| 指標 | GPUI 版 | 舊版 |
|---|---|---|
| 啟動到開始連 PTT | 163～214 ms | 635～661 ms |
| 閒置 CPU（行程樹合計） | 0.67% | 1.23% |
| PSS 記憶體 | 45 MB | 313 MB |
| RSS 記憶體 | 91 MB | 534 MB |
| 行程數／執行緒數 | 1／28 | 3／77 |
| 執行檔大小 | 16.9 MB | 25.1 MB |
| AppImage 大小 | 7.7 MB | 89.2 MB |
| release 編譯時間 | 2 分 52 秒 | 2 分 07 秒（不含 npm 安裝） |

記憶體差距來自 WebKitGTK：舊版光 Web 行程就近 300 MB。

### 下行管線吞吐量（離線，不含繪製）

| 輸入 | GPUI 版 | 舊版完整管線 | 舊版只算 xterm parser |
|---|---|---|---|
| 主選單畫面 65 KB | 0.53 ms／幀 | 6.38 ms／幀 | 0.91 ms／幀 |
| 歡迎畫面 4.3 KB | 0.05 ms／幀 | 1.03 ms／幀 | 0.07 ms／幀 |

舊版 85% 以上的時間花在補償鏈上，xterm 本身不到 15%。PTT 一幀最多數 KB，兩版都遠低於人眼可感，
這個數字說明的是架構負擔而非體感。

### 真實帳號操作（翻文章列表、看文章，每秒一鍵）

| 情境 | 指標 | GPUI 版 | 舊版 |
|---|---|---|---|
| 主選單閒置 | CPU | 0.61% | 1.99% |
| 文章列表翻頁 | CPU | 1.67% | 3.21% |
| 文章閱讀翻頁 | CPU | 1.52% | 2.25% |
| 全程 | PSS 峰值 | 57 MB | 327 MB |
| 每次按鍵到畫面更新（中位數） | 列表／閱讀 | 17.8／10.0 ms | 32／25 ms |

到 ws.ptt.cc 的網路往返只有 3.6 ms，舊版的延遲多半花在本機（WebKit 輸入、JavaScript、
補償管線、繪製）；GPUI 版扣掉網路後大半是在等下一個 vsync。

### 保留下來的效能修正

| 修正 | 做法 | 效果 |
|---|---|---|
| 按鍵延遲（`net.rs`） | 網路執行緒原本以 50 ms 逾時輪詢讀取，逾時後才送出按鍵。改成非阻塞 socket，以 `poll` 同時等 socket 與喚醒通道，UI 送鍵即喚醒 | 按鍵到新畫面：列表 48.8 → 17.8 ms、閱讀 36.8 → 10.0 ms；閒置時不再每秒醒來 20 次 |
| 圖片預覽記憶體（`image_preview.rs`、`view.rs`） | `img(Arc<Image>)` 會把解碼結果留在 gpui 的 asset 快取與 GPU 圖集，沒有釋放時機。改成自行解碼成 `RenderImage`，預覽收掉後以 `window.drop_image` 從圖集移除 | 連看 30 張 1080×1350 的圖：PSS 417 → 81 MB，收掉預覽後回到 61 MB；GPU 記憶體 311 → 87 MB |
| 動畫 GIF | gpui 一次把每一格解成整張畫布，解碼後總量超過 128 MB 的 GIF 只留第一格 | 記憶體有上限，移開即釋放 |

### GPU 用量

| 情境 | 指標 | GPUI 版 | 舊版 |
|---|---|---|---|
| 沒開 app | 整機 GPU 醒著的比例 | 10.6% | 10.7% |
| 主選單閒置 | app 的 GPU 忙碌比例 | 1.4% | 0.2% |
| | 整機 GPU 醒著的比例 | 66% | 12% |
| 文章列表翻頁 20 下 | app 的 GPU 時間 | 6.93 秒（35%） | 0.11 秒（0.5%） |
| | 幀數 × 每幀 GPU 時間 | 1,495 × 4.6 ms | 40 × 2.7 ms |
| 文章閱讀翻頁 20 下 | app 的 GPU 時間 | 6.38 秒（33%） | 0.10 秒（0.5%） |

**GPU 是 GPUI 版目前最大的弱點**，兩個原因都在 gpui 內部，app 端關不掉：

- **翻頁時**：gpui 在任何輸入（含滑鼠移動）後 1 秒內，每個 vsync 都把整個 scene 重畫一次。
  每幀成本只差不到 2 倍，差距來自幀數（約 1,500 對 40）。
- **閒置時**：兩版都是每秒約 2 幀（游標閃爍），但 gpui 另有每個 vsync 一次的空 commit，
  讓合成器每幀都要處理，GPU 一直進不了省電狀態。

實際耗電瓦數尚未量測。

## GPU 問題的上游狀態

**等上游，我們這邊沒得改。** 上面兩個行為都是 gpui 0.2.2 本身的問題，上游 Zed 已在 main 分支修好，
但 crates.io 最新版仍是 0.2.2，修正還沒發版。

| | 輸入後 1 秒內每幀都重送 | Wayland 閒置時每 vsync 空 commit |
|---|---|---|
| 0.2.2 程式位置 | `window.rs` 的 `on_request_frame` | `wayland/client.rs` 的 frame callback 循環 |
| 上游修正 | [#45369](https://github.com/zed-industries/zed/pull/45369)：只有 100 ms 內達 6 次的高頻輸入才保持出幀 | [#60690](https://github.com/zed-industries/zed/pull/60690)：沒東西要畫就停下迴圈 |
| 對應量測 | 翻頁約 1,500 幀、app GPU 33～35% | 閒置時整機 GPU 醒著 66% |
| 改動規模 | +59 −11，只動 `window.rs`，可直接套到 0.2.2 | +465 −62、8 個檔案，建立在之後的重構上 |

**處理方式：gpui 在 crates.io 發新版時升級並重量一次。**

**真的等不及時，最省事的過渡做法是只套 #45369**，但這要由維護者決定：

- 要 patch 就得把 gpui 原始碼放進 repo（8.1 MB、184 個檔案，用 `[patch.crates-io]` 指過去）
  或自己維護 fork，之後升版都要自己處理。
- #45369 風險低，預期能大幅降低翻頁時的 GPU 用量（未實測），但對閒置的 66% 沒有幫助。
- #60690 風險高：移植到 0.2.2 等於重寫 Wayland 出幀迴圈。上游還有未解決的
  [#64499](https://github.com/zed-industries/zed/issues/64499)（KDE Wayland 上畫面停住，要動滑鼠
  或按鍵才恢復）。PTT 的畫面更新來自網路資料而不是輸入，這正是本專案最怕的症狀。
- 直接改用上游 main 不划算：gpui 已拆成多個 crate、renderer 換成 wgpu，API 變動很大。

app 自己的部分維持現狀：閒置時那 1.4% 是 `view.rs` 的 500 ms tick，同時負責閃爍字、游標閃爍與
自動登入逾時檢查，視窗失焦且畫面上沒有閃爍字時會停止。舊版同樣每秒 2 幀，差別在 gpui 沒有局部重畫。
改它最多只省這 1.4%。等上游解決空 commit 後，游標閃爍會變成閒置時主要的 GPU 來源，屆時再評估
「停手數秒後停止閃爍」或「PTT 關掉游標且沒有閃爍字時不重畫」。

## 優缺點

GPUI 版的優點：

- 整條 xterm 補償鏈消失；寬字、雙色字、方塊彩繪在模型層就正確，不靠字型或 renderer 的巧合，
  也沒有一次性量測快取造成「測試綠、實機壞」的那類問題。
- 單一執行檔、啟動不經 WebView，沒有 npm 供應鏈。CPU 與記憶體用量低很多。
- 測試直接驗網格狀態。

GPUI 版的缺點與風險：

- **GPU 用量遠高於舊版**（見上節）。
- **只有 Linux**；macOS 與 Windows 未建置測試，舊版靠 Tauri 三平台都走過。
- **編譯成本高**：gpui 依賴龐大，第一次編譯數分鐘，`target/` 數 GB。
- **Linux 建置門檻**：只走 Vulkan，無 OpenGL 或軟體後備；需要多個 `-dev` 套件。
- **gpui 0.2 API 不穩定**，升版可能要改程式；文件稀薄，很多用法要讀 Zed 原始碼。
- **字形垂直位置針對 Noto CJK 硬編碼**（`view.rs` 的 `center_ratio`），換字型要重調。
- **PTT 若開始送新的終端控制序列，畫面會先壞**（見下節）。

## PTT 官方改版時的影響

兩版都只照實顯示伺服器送來的畫面，大部分改版影響相同：

| 改版內容 | 兩版的反應 |
|---|---|
| 選單、看板、版面的文字或排版 | 都不解析畫面，照常顯示 |
| 登入提示文字 | 都靠比對提示文字自動登入；比對不到就退回手動，不重試 |
| 編碼切換時機（Big5／UTF-8） | 都是自己實作的雙軌切換，兩邊都要跟著修 |
| WebSocket 端點、telnet 協商 | 都是自己寫的，風險相同 |

差別在終端模擬器：舊版由 xterm.js 繪製，沒見過的序列多半也能正確顯示；GPUI 版的 `grid.rs`
只實作 PTT 目前會送的序列，沒實作的記進 `unknown_sequences` 印到 stderr，畫面可能錯位或留殘字。
實際風險不高：終端序列是 PTT 最少變動的一層，stderr 會指名是哪一個序列，通常在 `grid.rs`
加一個分支、補一個測試就能修好。

## 兩種技術路線本身

| | WebView（Tauri 2 + xterm.js） | GPUI 自繪 |
|---|---|---|
| 強項 | 跨平台幾乎免費；排版、IME、無障礙、高 DPI 由瀏覽器解決；DevTools 成熟；無 GPU 也能跑 | 為文字密集介面而生；低階繪圖路徑開放，半字、劈字幾十行解決；單一小執行檔 |
| 弱項 | 資源開銷是結構性的；三平台引擎不同；抽象層與領域模型不合時代價極大 | 編譯慢、API 變動大、文件少；沒有元件庫；無障礙與跨平台成熟度不足；單一供應者 |

GPUI 的強項正是 PTT 客戶端的核心需求，弱項正是本專案幾乎不碰的部分。要權衡的是編譯與依賴帶來的
維護負擔，以及 API 不穩的升版風險：把 gpui 版本釘死、固定週期升一次，可以把風險收斂到可控的時間點。
